## Registry discovery: what is supported now

The [public catalog](https://aureformui.com/r/registry.json) returned 107 items, with no `content` property in its catalog file records. The [button payload](https://aureformui.com/r/button.json) returned installable source content and Base UI dependencies. These are different files with different purposes. The initial documentation review inspected HTTP/JSON structure. A subsequent [October 20 readiness check](promotion/registry-readiness.md) ran the original upstream validator against a single-entry fixture and installed Button and the appearance provider in a fresh Next.js consumer. TypeScript, a production build and a scoped interaction probe passed; the fixture recorded a missing-favicon warning. That evidence covers two items and one configuration, rather than all registry entries or official acceptance.

The official index route uses a proposed namespace such as **`@aureform`** and URL `https://aureformui.com/r/{name}.json`. That namespace was absent in the inspected directory; it is neither reserved nor published. The [draft](promotion/github-submissions.md#official-shadcn-registry-directory) includes the required original SVG logo. The consumer check supplied this mapping manually. Before an authorized submission, recheck the namespace and procedure, run any required full upstream checks and attach the [recorded results](promotion/registry-readiness.md). The local validator check did not run the root **`pnpm validate:registries`** wrapper or validate the other 479 entries. [Directory procedure](https://ui.shadcn.com/docs/registry/registry-index), [actual validator](https://github.com/shadcn-ui/ui/blob/main/apps/v4/scripts/validate-registries.mts).

The current shadcn documentation also supports public GitHub registry addresses without admission to the namespace directory. Aureform has a root `registry.json`, but this research did not verify its GitHub-address transport with a current consumer. Keep the documented full-URL command as the advertised route until that separate check passes. [Official GitHub registry distinction](https://ui.shadcn.com/docs/registry/registry-index), [GitHub registry guide](https://ui.shadcn.com/docs/registry/github).

## External submission workflow

The drafts are review material, **not authorization to publish**. Any external PR, issue, discussion, message or form submission needs explicit user authorization for that destination and content. The awesome-shadcn website form creates a PR, so it is also an external write. Authorization does not override a destination's human-only or editorial rules.

Before each authorized submission, re-read the guide/template, check existing entries and pending PRs, reproduce the relevant release example, disclose the maintainer affiliation and make one focused change in the exact listed file. Complete template confirmations only for checks actually performed. For the design-system table, carry the frozen-Figma caveat in the PR body; for the registry directory, carry the current consumer/validator results.

After a response, incorporate requested edits into the same PR and respect rejection. Reassess manually when a release changes the project, when a maturity gate is met, or before another submission. No bot stars, keyword stuffing, paid promotion, repeated promotional issues, claimed GitHub endorsement or guaranteed placement. This research configures no recurring monitoring.
